# План решения: AI-агент для табличных ML-задач

Документ описывает архитектуру и все ключевые решения системы. Код в этом архиве реализует план целиком.

---

## 0. Что следует из условий

| Условие | Следствие для архитектуры |
|---|---|
| Итог считается на **двух скрытых задачах**, которые агент видит впервые | Главное — надёжность и универсальность. Падение на приватной задаче = ноль. Любой этап должен иметь детерминированный запасной путь. |
| Обратной связи от платформы нет | Единственный сигнал качества — собственная кросс-валидация. Её нужно защищать от переобучения (находка AIRA-dojo: выбор решения по валидации систематически переоценивает качество). |
| Данные табличные, 8 CPU, 32 GB, без GPU и интернета, предобученные модели запрещены | Ядро — градиентные бустинги (LightGBM, CatBoost, XGBoost) + ансамбль. Нейросеть только как дополнительный член ансамбля. TabPFN и подобное недоступны. |
| Единственная LLM — Qwen3.8-27B | Модель среднего размера: короткие сфокусированные промпты, правки в узких «слотах» кода, строгий JSON, проверка всего, что она говорит. Длинные свободные скрипты от 27B-модели ненадёжны. |
| `AGENT_TIME_BUDGET` по умолчанию 3 часа на задачу | Anytime-поведение: валидный сабмит в первые минуты, затем только улучшения. Распределение времени по фазам адаптивное. |
| Задачи запускаются изолированно | Никакого переноса знаний между задачами, кроме встроенных в код рецептов. |

## 1. Принципы (из исследований 2025–2026)

1. **Поиск в пространстве кода с операторами «черновик / отладка / улучшение»** (AIDE). Каждый эксперимент — узел с кодом и оценкой, а не реплика в диалоге.
2. **Качество операторов важнее алгоритма поиска** (AIRA-dojo). Вместо сложного MCTS — сильные специализированные операторы гипотез и строгий оценщик.
3. **Точечные правки по компонентам пайплайна** (MLE-STAR). LLM никогда не переписывает весь пайплайн: она добавляет один блок признаков или одно структурное действие.
4. **Разделение «исследователь / разработчик»** (R&D-Agent). Researcher (с рассуждением) выдвигает гипотезы, Developer пишет код, Debugger чинит.
5. **Раздельный поиск признаков и моделей** (TabFM-Auto). Одновременный перебор признаков, моделей и гиперпараметров даёт шумный сигнал. Поэтому: фаза 1 — признаки при фиксированной прокси-модели; фаза 2 — модели и гиперпараметры при фиксированных признаках.
6. **Память и сжатие контекста** (ML-Master 2.0). Журнал экспериментов хранится полностью, а в промпт попадает сжатое представление: свежие записи целиком, старые — агрегатом, плюс список «выводов», который ведёт сам Researcher.
7. **Контроль исполнения отдельно от научных решений** (ScienceFlow). Оркестратор (обычный код) владеет временем, таймаутами, ресурсами и правом остановить эксперимент. LLM этим не управляет.
8. **Структурная защита от утечек вместо LLM-критика.** Код признаков физически не получает целевую переменную; target encoding делается только внутри фолдов системой.

## 2. Архитектура

```
solution.py ── гарантия сабмита (try/except + аварийный fallback)
   │
   └─ Orchestrator (детерминированный код; дедлайны, ресурсы, anytime-сабмит)
        │
        ├─ Фаза A. Данные: поиск файлов → надёжное чтение → профиль колонок
        │
        ├─ Фаза B. Понимание задачи
        │     Heuristic TaskSpec (регэкспы, sample_submission, data_dictionary)
        │     ∥ LLM Analyst (параллельно с бейзлайном) → JSON
        │     → Reconciler: проверка фактов кодом, выбор метрики, формата, CV-схемы
        │
        ├─ Фаза C. Бейзлайн-страховка: LightGBM CV → сабмит за первые минуты
        │
        ├─ Фаза D. AutoResearch по признакам (асинхронный цикл)
        │     Researcher (LLM, thinking) ── гипотезы JSON ──┐
        │     Auto-гипотезы (детерминированные) ────────────┤→ очередь
        │     Developer (LLM) → код блока → Песочница (subprocess, таймаут)
        │     Debugger (LLM) ← traceback (≤2 попытки)
        │     Evaluator (прокси LightGBM, фиксированные фолды, парный тест)
        │     Журнал + выводы → обратно Researcher'у; инкумбент обновляется
        │     Подтверждение на свежих фолдах (анти-переобучение)
        │
        ├─ Фаза E. Модели: Optuna-LightGBM, CatBoost, XGBoost, варианты
        │     таргета/весов, MLP; финальные фолды с новым сидом; multi-seed
        │
        └─ Фаза F. Ансамбль (hill-climbing ∥ стекинг) → постобработка под метрику
              → сборка сабмита в формате sample_submission → валидация → запись
```

LLM-вызовы идут в фоновых потоках и перекрываются с вычислениями на CPU: пока бустинг считает текущую гипотезу, модель пишет код следующей.

## 3. Бюджет времени (по умолчанию 3 часа, всё в долях)

| Фаза | Доля | Комментарий |
|---|---|---|
| A+B+C | ~4–6% | Профиль, понимание задачи, бейзлайн-сабмит |
| D (признаки) | до ~38% | Досрочный выход: нет идей, исчерпан LLM-бюджет, плато |
| E (модели) | ~45% | Очередь кандидатов с оценкой стоимости; каждый кандидат проверяет остаток времени |
| F + резерв | ~6% + запас | Ансамбль, постобработка, запись; резерв на непредвиденное |

При малом бюджете (например, 10 минут) все фазы пропорционально сжимаются; при отсутствии LLM фаза D сокращается до auto-гипотез, а время уходит на модели.

## 4. Детерминированное ядро

### 4.1 Загрузка
- Файлы по точным именам, затем по ключевым словам (`train`, `test`, `sample|submission`, `dict|description`).
- Кодировки `utf-8`, `utf-8-sig`, `cp1251`, `latin-1`; авто-определение разделителя.
- `id` читается как строка (сохраняются ведущие нули), выход строится по порядку строк `sample_submission`.
- Сырые строковые токены таргета сохраняются, чтобы метки на выходе были записаны ровно как в train (`1`, а не `1.0`).

### 4.2 Профиль
Для каждой колонки: тип, пропуски (train/test), уникальные значения, примеры, квантили, признаки ID/константы/даты/текста, доля пересечения значений train↔test. Плюс adversarial validation (train vs test) с топом «дрейфующих» признаков. Компактные текстовые сводки с лимитом символов для промптов.

### 4.3 TaskSpec
- **Цели и ID**: из `sample_submission` (колонки, отсутствующие в test), подтверждение по `data_dictionary.role`.
- **Тип задачи**: тип таргета, число классов, подсказка метрики.
- **Метрика**: приоритет строк вида «Метрика:», «Основная метрика» (так справочные Accuracy и Weighted F1 из условия не перебивают Macro F1), затем LLM. Реестр: RMSE, MSE, MAE, RMSLE, MAPE, SMAPE, R², MedAE, Accuracy, Balanced Accuracy, F1 (binary/macro/micro/weighted), Precision/Recall, MCC, Cohen/Quadratic Kappa, ROC-AUC (binary/OVR), Gini, PR-AUC, LogLoss. Неизвестная метрика — код от LLM с проверкой на игрушечных данных, иначе суррогат.
- **Формат ответа**: метка / вероятность положительного класса / матрица вероятностей / число — по метрике и содержимому sample. Положительный класс: `1`/`True`/`yes`, иначе по LLM, иначе миноритарный.
- **Reconciler**: факты (существование колонок, совпадение с sample) проверяет код; LLM может уточнить только то, что код не может определить надёжно.

### 4.4 Препроцессинг (без таргета)
- Удаление ID-подобных и константных колонок; bool → int; строки-числа → числа.
- Даты → год, месяц, день, день недели, день года, timestamp.
- Длинный текст → длина, число слов, TF-IDF + SVD.
- Категориальные: общий словарь категорий train+test, редкие категории склеиваются; высокая кардинальность → count encoding + target encoding внутри фолдов.

### 4.5 Схема валидации
- Классификация: StratifiedKFold; регрессия: KFold, стратифицированный по квантилям таргета.
- **Групповая CV** включается, только если есть колонка-сущность, значения которой повторяются в train, но почти не встречаются в test (значит, test — новые сущности).
- **Временная CV** — если test лежит позже train по дате.
- Прокси-фолды (фаза D) и финальные фолды (фаза E) используют разные сиды: финальные OOF-оценки честнее.

### 4.6 Target encoding внутри фолдов
Для каждого внешнего фолда: на обучающей части — OOF-кодирование по внутренним фолдам, на валидации и тесте — статистики обучающей части. Сглаживание m-estimate. Мультикласс — вероятность каждого класса. Комбинации колонок кодируются как составной ключ. Так «сущностные» признаки (например, одно и то же здание в разные годы) работают без утечки.

## 5. Агенты и промпты

Все промпты на английском (точнее выполняются), данные и описания — как есть (русский). Каждый промпт: роль → контекст задачи → строгий контракт вывода → правила/подводные камни → формат ответа.

| Агент | Вход | Выход | Режим |
|---|---|---|---|
| **Analyst** | task.md, data_dictionary, профиль, head sample/train, эвристическая догадка, список метрик | JSON TaskSpec + доменная сводка + идеи признаков + подозрения на утечки | thinking, t=0.6 |
| **Researcher** | сводка задачи, словарь, текущие признаки, важности, анализ ошибок (по классам / по сегментам остатков), adversarial, журнал, выводы | 4–6 разнообразных гипотез JSON (тип, обоснование, спецификация, ожидаемый эффект) + обновлённые выводы | thinking, t=0.7 |
| **Developer** | гипотеза, колонки с типами/примерами/описаниями, контракт `transform(df)` | один python-блок | thinking (откат на no-think при обрезке) |
| **Debugger** | код, traceback, колонки | исправленная функция | как Developer |
| **Metric coder** (редко) | описание метрики | `def metric(y_true, y_pred)` | thinking |

Типы гипотез: `feature_code` (код), `target_encoding` (списки колонок), `drop_features`, `categorical_cast`. В промпт Researcher встроены знания о том, что работает с бустингами (отношения семантически связанных величин, групповые агрегаты, ключи сущностей + count/TE, агрегаты семейств колонок, сентинельные значения), и что бесполезно (монотонные преобразования одной колонки, one-hot, случайная арифметика).

## 6. Цикл AutoResearch (фаза D)

1. **Auto-гипотезы** (без LLM, считаются первыми, пока LLM думает): count encoding, TE высококардинальных и всех категорий, TE пар топ-категорий, число пропусков в строке, число дубликатов строки, числовые-как-категории, групповые статистики топ-признаков, удаление нулевых по важности.
2. **LLM-гипотезы**: Researcher → очередь → Developer → песочница → оценка.
3. **Песочница**: subprocess с таймаутом и лимитом памяти, статическая проверка запрещённых конструкций (IO, сеть, subprocess, eval), проверка результата (длина, inf→NaN, лимит числа колонок, константы).
4. **Оценка**: прокси-LightGBM с фиксированными параметрами и фолдами, скорость калибруется по бейзлайну (lr, число фолдов, сабсэмпл для больших данных).
5. **Критерий принятия** — парный тест по фолдам: `mean(Δ) > max(min_gain, z·SE(Δ))`. Сравнение на одних и тех же фолдах убирает большую часть шума.
6. **Жадное накопление**: принятый блок становится частью инкумбента; сабмит обновляется сразу.
7. **Near-miss бандл**: гипотезы с положительным, но незначимым приростом в конце проверяются вместе.
8. **Подтверждение**: инкумбент против исходных признаков на свежих фолдах; если прирост не подтвердился — откат.

## 7. Модели (фаза E)

Очередь кандидатов по приоритету с оценкой стоимости по замерам:
1. LightGBM + Optuna (TPE, прунинг по фолдам, стартовая точка — проверенные дефолты), финальное обучение с меньшим learning rate.
2. CatBoost (нативные категории, бюджет итераций по замеру скорости).
3. XGBoost (hist, нативные категории).
4. Варианты под метрику: регрессия — log1p-таргет, Huber/L1; классификация — веса классов (для macro-метрик).
5. MLP (PyTorch, эмбеддинги категорий, квантильная нормализация) — ради разнообразия ансамбля.
6. Дополнительные сиды лучших моделей, пока есть время.

## 8. Ансамбль и постобработка (фаза F)

- **Hill-climbing** (Caruana, с повторами) по OOF и **стекинг** (LogReg/Ridge на OOF с честной вложенной CV); выбирается лучший с допуском в пользу простого.
- Целевая функция бленда: сама метрика для непрерывных выходов, logloss — для метрик на метках.
- **Постобработка под метрику** (подбирается на OOF, применяется к тесту только если выигрыш подтверждается на половинках OOF):
  - Macro-F1/Balanced Acc мультикласс → веса классов (покоординатный подъём);
  - бинарный F1/MCC/Kappa → порог;
  - LogLoss → temperature scaling + клиппинг;
  - регрессия → клиппинг в диапазон таргета, неотрицательность, линейная калибровка.

## 9. Сабмит и гарантии

- Первый валидный `submission.csv` — сразу после бейзлайна; затем перезапись только при улучшении OOF.
- Атомарная запись (tmp + rename), проверка: те же колонки и порядок строк, что в sample, нет NaN, правильные типы.
- Если всё упало — аварийный сабмит (среднее/мода/априорные вероятности) в формате sample.

## 10. Надёжность и ресурсы

- Реальное число CPU — по cgroup (`cpu.max`) и affinity, а не `os.cpu_count()`; от этого зависят `n_jobs` всех моделей.
- Каждый этап в try/except; ошибки пишутся в лог и отчёт, система идёт дальше.
- LLM: health-check с ретраями в фоне; при недоступности — полностью детерминированный режим. Ретраи с backoff на 429/5xx/таймауты; вырезание `<think>`; извлечение JSON с ремонтом и повторным запросом; откат с thinking на no-think при обрезке.
- Промежуточные файлы — только в `<task_dir>/.agent_work` (или `/tmp`).

## 12. Что добавлено по итогам реализации и тестов

- **Поиск «ключа сущности» без LLM.** Жадно собирается набор колонок, постоянных внутри одной сущности и повторяющихся между train и test (например, одно здание в разные годы: площадь + штат + класс + тип). Ключ получает count encoding и target encoding внутри фолдов. На синтетике по зданиям это снижает RMSE прокси-модели с 37.97 до 26.88 — самый сильный одиночный приём для задач с повторяющимися сущностями.
- **Target encoding точных дубликатов строк** — для данных с массовыми повторами записей (сетевой трафик).
- **Неблокирующий Analyst.** Если метрика явно указана в тексте и формат однозначен по sample_submission, исследование стартует сразу, а идеи Analyst подмешиваются в цикл по готовности. Цикл подхватывает LLM, как только завершился health-check.
- **Распределение времени в фазе моделей по долям с перетеканием остатка** и выбор learning rate по замеренной скорости (пробный запуск для XGBoost/CatBoost). Модели, которым не хватает итераций для сходимости, пропускаются, а их время уходит следующим.
- **AutoGluon-Tabular как один из членов ансамбля** (bagging 5 фолдов, свои нейросети и деревья) — источник разнообразия поверх наших бустингов. Ему передаются наши инженерные признаки и OOF-версия target encoding (без неё он проигрывал: RMSE 34.8 против 25.9 с ней на синтетике по зданиям). Отключается `AGENT_USE_AUTOGLUON=0`; любая ошибка не влияет на остальное.
- **Ускорения:** векторизованный подбор весов классов (в 18 раз быстрее), быстрые label-метрики через матрицу ошибок, кэш решений для одиночных моделей, стекинг с ограничением по времени, XGBoost с one-hot малых категорий и частотными кодами больших (в 35 раз быстрее на мультиклассе).
- **Проверенная регистрация нестандартной метрики:** код от LLM проверяется на игрушечных данных (конечность, направление) до использования.
- **Завершение без ожидания фоновых HTTP-запросов** (`os._exit` после записи сабмита), чтобы не выйти за бюджет.

## 13. Итерация 2: разбор прогонов на платформенных данных

**Реконструкция задач.** Публичные задачи удалось воспроизвести точно, с ответами для честной проверки:
- мультикласс — train взят из оригинального обучающего набора UNSW-NB15, test — из оригинального тестового (размеры ровно половинные; adversarial AUC 0.8846 совпадает с логами платформы до третьего знака);
- регрессия — WiDS Datathon 2022: train = годы 1–5 (53 308 строк), test = год 6 (22 449), единицы переведены в метрику, как на платформе.

**Что показали эксперименты на тесте:**

| Задача | Вывод | Решение |
|---|---|---|
| Регрессия | ключ сущности (здание) — главный рычаг: 42.2 → 36.2 RMSE; случайная CV ранжирует варианты так же, как тест | оставлено |
| Регрессия | история сущности по предыдущим периодам: 36.2 → 35.9; удаление колонки периода: → 35.5 | новые auto-гипотезы |
| Мультикласс | CV завышает на ~0.11 (0.64 против 0.53) из-за сдвига; порядок вариантов по CV не совпадает с тестом | ансамбли для устойчивости |
| Мультикласс | правило решения (веса классов) +0.05 и на тесте | оставлено |
| Мультикласс | EM-коррекция априорных частот (Saerens 2002): −0.10 | не используется |
| Мультикласс | обучение и валидация с весами важности (adversarial density ratio): −0.06 / не предсказывает тест | не используется |
| Мультикласс | разброс одиночных моделей на тесте ±0.03 больше разницы стратегий; ансамбль держится у среднего | прямая оптимизация macro F1 в ансамбле |

**Исправлено и добавлено:**
- `submission.csv` (свой выход прошлого запуска) больше никогда не принимается за `sample_submission`.
- Распознавание будущего периода (`detect_period`) → гипотезы «история сущности» (последнее/среднее значение таргета той же сущности в прошлых периодах, число наблюдений, разрыв) и «удалить колонку периода». Случайная CV не видит их эффекта, прямые фолды по одному периоду оказались слишком шумными (год 4: +0.58, год 5: −2.34), а на тесте обе стабильно помогают (история −1.15 RMSE, удаление года — улучшение в 3 из 3 сравнений). Поэтому они принимаются по правилу, если CV не показывает явного вреда (хуже 2 SE).
- AutoGluon обучается внутри наших фолдов (по одному обучению на фолд, бэггинг внутри обучающей части). Раньше он получал target encoding, посчитанный на внешних фолдах, и его OOF был нечестным (CV 34.8 против теста 37.0); ансамбль давал ему вес 0.67 и проигрывал на тесте до 0.7 RMSE. Теперь CV 36.0 против теста 36.3.
- Порог приёма гипотез растёт с числом проверенных (z от 1.0 до 1.5) — поправка на множественные сравнения.
- Замер скорости моделей по разнице двух пробных запусков (раньше подготовка фолдов завышала оценку в 10–30 раз, и CatBoost/XGBoost почти всегда пропускались).
- CatBoost: ключи с >2000 уровнями идут частотными кодами (они уже закодированы target encoding'ом), а не строковыми категориями.
- Параллельное обучение фолдов для LightGBM и CatBoost (XGBoost исключён: конфликт OpenMP между потоками даёт 70-кратное замедление).
- Отсутствующая библиотека модели исключается из плана; HPO останавливается после трёх неудач подряд.
- Ансамбль: финальный бленд подбирается по самой метрике с правилом решения в цикле (для label-метрик).
- Кэши target encoding и представлений моделей учитывают данные, а не только имена колонок.
- Промпт Researcher при сильном сдвиге (adversarial AUC > 0.8) предупреждает об оптимистичной CV.
